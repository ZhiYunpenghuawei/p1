# Beam Session 契约 V1（中文翻译）

> 原文：`docs/beam_session_contract_v1.md`（PR #292 引入）

## 状态与范围

Beam Session 契约 V1 是一套带版本号的、与运行时无关（runtime-neutral）的词汇表和 CPU 参考实现，服务于未来的批量 Beam 执行。协议版本为 `1`。

本契约**不**把 Beam 执行与 Serving、EngineCore、Scheduler、Worker/ModelRunner、KV 管理、约束资源加载或 Online/Offline 入口连接起来。这些集成需要后续的生命周期和运行时改动。

实现归属：

- `vllm_gr/v1/beam/contracts.py`：被动数据契约与校验；
- `vllm_gr/v1/beam/reference.py`：确定性的 CPU 选择语义。

## 生命周期词表

`BeamSessionStage` 冻结以下阶段值：

```text
waiting          等待
prefilling       预填充
prefill_ready    Prefill 就绪
decoding         解码中
finalizing       收尾中
draining         排空中
finished         已完成
aborted          已中止
failed           已失败
```

本 PR 只定义词表，不在任何现有运行时所有者上安装状态机。

### Epoch 事务规则

`step` 是逻辑解码位置。`epoch` 是会话内单调递增的执行事务号，由未来的 Coordinator 分配。这些共享术语的含义：

- `next_epoch` 是下一个可分配的值；
- dispatch（下发）时把该值移入 `in_flight_epoch`，并推进 `next_epoch`；
- 一个逻辑 step 的每个物理分片都携带相同的 in-flight `step` 和 `epoch`；
- 只收到一个 epoch 的部分分片时，`completed_epoch` 不变，也不能提交 sequence、constraint 或 Beam KV 状态；
- 一次完整成功的 Worker 事务把 in-flight epoch 恰好一次地移入 `completed_epoch`；
- 过期的、重复的或非 in-flight 的分片/结果一律 fail-closed（直接拒绝）；
- 批级 Worker 错误使 Session 走向 `FAILED`，清空或排空 in-flight 事务，且不会自动重试或复用该 epoch。

本契约不要求这些计数器一定放在 Worker 里。未来的 Coordinator 负责调度相关性（scheduling correlation）；Worker 负责 Beam 状态的原子提交。

## 稳定行身份

`BeamRowIdentity` 由以下字段组成：

```text
batch_session_id     业务 Session ID
child_request_id     对应的原生 child Request ID
step                 逻辑解码位置
epoch                执行事务号
item_index           item 下标
beam_lane            beam 下标
physical_fragment_id 物理分片编号
```

`item_index` 和 `beam_lane` 是 0 基的。物理数组的偏移量或行位置**不是**身份。重排物理行必须保持每个 `BeamRowIdentity` 不变，且不能改变逻辑选择结果。

`physical_fragment_id` 是从所在 `WorkerBeamStepFragmentInputV1` 拷贝过来的 0 基分片编号；它不是从行的当前位置推导出来的。物理分片划分的是逻辑执行行，而不是候选词表。因此，一个 `(batch_session_id, step, epoch, item_index, beam_lane)` 逻辑行在一个 epoch 的所有分片中只能出现一次。分片精确重放（replay）和逻辑行重叠（overlap）是两种不同的协议错误。

## Batch Admission（准入）

`BatchBeamRequestV1` 包含 Beam 特有的业务数据：

- 协议版本与批 Session 身份；
- 一个连续、下标唯一（contiguous, uniquely indexed）的 `BatchBeamItemV1` 集合；
- 搜索宽度、带版本号的输出规格、最大解码步数；
- temperature 与特殊 token ID；
- EOS / 输出策略标志；
- 带版本号的约束 `resource_id`。

每个 item 只包含 `item_index`、`child_request_id` 和 prompt token ID。child Request ID 在一个批内唯一。

`beam_width` 是活跃搜索前沿的宽度。`output_spec.result_width` 是每个 item 返回的最终结果上限，满足 `0 < result_width <= beam_width`；它不会收窄中间的搜索步。`begin_token_id` 和 `end_token_id` 是可选的。temperature 是有限非负数，包括确定性的 `0.0` 运算。

`BeamOutputSpecV1` 冻结了后续 Final Result 契约所需的请求侧要求：

```text
wire_version = 1
result_width
logprobs_mode = none | selected | top_k
top_logprobs
include_scores
include_parent_lineage
```

`top_logprobs` 只在 `top_k` 模式下为正，在 `none` 或 `selected` 模式下为 0。本 PR 不定义最终载荷或前端格式化；它只是防止后来的 adapter 反过来改变 admission ABI。

本契约不包含 tokenizer、Catalog/Trie 对象、Serving 请求、完整约束表、EngineCore 对象或 Scheduler 对象。LoRA、优先级、数据并行 rank 等通用执行属性仍是原生 engine request 的属性，不在这里重复。

V1 准入对除 `"default"` 之外的所有 `resource_id` 一律 fail-closed。

## Scheduler Continuation（续跑指令）

`BeamContinuationV1` 只说明某个 item 下一步执行什么：

```text
batch_session_id + child_request_id + item_index
step + epoch
lane_token_ids[W]
parent_indices[W]
active_width
```

两个 lane 数组都具有固定的批 beam 宽度。活跃 lane 占据前缀 `[0, active_width)`。每个非活跃的尾部 lane 携带 `INVALID_TOKEN_ID == -1` 和 `INVALID_PARENT_INDEX == -1`。

一个 continuation **不能**包含完整序列、累积分数、约束节点、已完成的假设或 W×K 候选矩阵。

## Worker Step Fragments（Worker 步分片）

`WorkerBeamStepFragmentInputV1` 表示一个完整逻辑 Worker epoch 的一个稀疏物理分片：

```text
batch_session_id + step + epoch
batch_size + beam_width
fragment_index + fragment_count
expected_row_count
row_identities[R]
sparse continuations
resource_id
```

`fragment_index` 在 `[0, fragment_count)` 内。每个分片非空，且该 epoch 的所有分片携带相同的 batch/width/count 元数据。`expected_row_count` 是完整 epoch 预期的不同逻辑行总数，而不是当前分片的行数。

分片内的 continuation 使用全局 item 下标，可以描述稀疏集合（如 `{2, 3}`），不会在本地重编号。每行引用该分片的某个 continuation 的某个活跃 lane。未来的 StepAccumulator 可以在所有分片编号和所有预期逻辑行都齐了之后，才运行全局的 per-item Top-W 并原子提交该 epoch。

V1 在内部 ABI 中携带稳定的 `resource_id == "default"`。进程内的 `ConstraintResourceHandle` 在 Worker 内部绑定和持有，绝不会在本契约中被序列化。

`WorkerBeamStepResultV1` 返回固定的矩形值：

```text
selected_token_ids[B, W]
parent_indices[B, W]
active_mask[B, W]
terminal_mask[B]
finished
error
```

它还回显 `protocol_version`、`batch_session_id`、`step` 和 `epoch`，使消费方可以拒绝错误事务的响应。

对每个非活跃 lane：

```text
active_mask[b][w] is False
selected_token_ids[b][w] == -1
parent_indices[b][w] == -1
```

活跃 parent 下标在 `[0, W)` 内。terminal item 没有活跃 lane，`finished` 等于 `all(terminal_mask)`。

成功结果 `error is None`。它描述的状态已经在未来的 Worker 所有者内部提交：sequence 状态、约束状态和 Beam KV 谱系不需要 EngineCore 确认。因此该结果没有确认或回滚字段。

失败结果带有非空的批级 `error`，所有 item terminal，`finished is True`，每个 lane 非活跃，并且只有 `-1` token/parent 哨兵。它不包含任何已提交的选择，并使 Session 走向 `FAILED`。成功和失败的表示互斥。结束原因和 per-item 错误映射由后续的 Output 和 Lifecycle 工作负责。

重放检测是上下文相关的。Worker 分片校验接收先前见过的 fragment key 和 logical-row key，以拒绝精确重放和重叠。结果校验接收已提交的 `(batch_session_id, step, epoch)` key。成功的多分片结果还要求 accumulator 证据覆盖每个分片编号并且恰好 `expected_row_count` 个逻辑行；致命错误可以终止部分 epoch 而不假装它完整。本模块只负责校验，不持有或修改那些 accumulator 和 Coordinator 集合。

## 集中校验

所有协议边界都使用：

```text
validate_batch_beam_request
validate_beam_continuation
validate_worker_step_input
validate_worker_step_result
```

校验抛 `BeamContractError`，它是 `ValueError` 的子类。协议校验不使用 `assert`，也不依赖 dataclass 构造副作用。

除其他不变量外，校验器强制执行：版本 1、非空 ID、child 唯一、admission item 下标全局连续、分片稀疏 item 下标在准入批范围内、Beam/输出宽度为正、分片数与行总数合法、step/epoch/fragment 坐标为非负整数、逻辑行不重叠、结果 B/W 形状固定、parent 合法、哨兵一致、成功/失败结果互斥，以及 V1 资源准入规则。

## 确定性 CPU Reference

Reference 暴露三个稳定操作：

1. `candidate_select`：去掉仅用于传输的 sampled 槽位，接收调用方已算好的合法候选 mask，拒绝重叠逻辑行，并计算累积分数。
2. `beam_select`：先完成 terminal 候选，再选择活跃 Top-W；W 恒为 `beam_width`，且对每个 item 独立进行。
3. `final_select`：按 `result_width` 给已完成结果排序；当 item 没有任何完成时，回退到活跃结果（即 max-step 收尾行为）。

它不导入或操作 Serving、EngineCore、Scheduler、Worker、`BeamSearchSequence`、Trie 或设备张量。

### FlatLogprobs 布局

契约 V1 冻结每个候选行格式为：

```text
[sampled, top1, ..., topK]
```

slot 0 是传输附件，永远被忽略。Reference 只消费 `top1...topK`，去掉 slot 0 后候选 rank 从 0 开始。

这与 legacy helper 的"条件式 sampled token 去重"故意不同。现有 Serving 和 Offline 行为不变。

### 稳定排序

每次选择都使用以下升序排序 key，它表达的是文档化的"候选分数降序"：

```text
(-cumulative_score,
 parent_beam_index,
 candidate_rank,
 token_id,
 original_candidate_index)
```

原始候选下标来自稳定的物理分片身份和候选 rank，而不是当前行位置。CPU、GPU、NPU 实现都可以把这个 Reference 当作并列打破（tie-break）的裁判。

### 约束耗尽

非有限候选永远不会被选来凑宽度。如果某个 item 没有合法的活跃或 terminal 候选，`beam_select` 返回：

```text
constraint_exhausted = True
active_width = 0
```

把这个状态映射成结束原因或 per-item 错误，属于契约 V1 之外的工作。

## 兼容性边界

在分数不并列、且 sampled 槽位规则没有差异时，CPU Reference 与现有 legacy 决策 helper 在 token、score、parent 和 terminal 语义上一致。契约 V1 只在未来运行时实现中改变 tie 顺序和 sampled 槽位处理；本 PR 不会把任何现有入口切换到新行为。
